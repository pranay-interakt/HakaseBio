# 07 — Data Model & Provenance

> Status: describes code that exists in `backend/hos/core`, `backend/hos/kernel` and
> `backend/hos/db`. Anything not yet implemented is marked **(planned)**.

This document is the integrity core of the system. Every other component depends on the rules
here, and the rules are enforced by constructors, not by convention: an object that would violate
them cannot be created.

---

## 7.1 `Quantity` — the only way a scientific number exists

`hos/core/quantity.py`. A frozen dataclass binding:

| field | type | meaning |
|---|---|---|
| `value` | `float \| None` | the magnitude; `None` only for `UNAVAILABLE` |
| `unit` | `str` | parsed by the shared `pint` registry at construction; an unknown unit raises |
| `provenance` | `Provenance` | how the value came to exist (§7.2) |
| `uncertainty` | `Uncertainty \| None` | `ci95`, `sd`, `sem` or `range`, in the same unit |
| `label` | `str \| None` | human name shown in the UI |
| `qc_flags` | `tuple[str, ...]` | QC codes that travel with the value and propagate to derived values |

Invariants enforced in `__post_init__`:

- `UNAVAILABLE` ⇒ `value is None`; every other kind ⇒ a finite real number. NaN and ±inf are
  rejected, because they indicate a failed computation that would otherwise propagate silently.
- The unit must parse. Conversions (`.to()`, `.magnitude_in()`) are real dimensional algebra via
  `pint`; incompatible dimensions raise. A conversion appends a note to the provenance.
- `require()` returns the magnitude or raises `QuantityError` naming the reason the value is
  unavailable. Code calls it at the exact point a real number is needed, so a missing input becomes
  an explicit error rather than a default.

Constructors: `measured`, `literature`, `computed`, `predicted`, `guideline`, `user_supplied`,
`unavailable`. There is no constructor that produces a number without provenance.

**Identity.** `Quantity.id` is a content hash (`q_` + 20 hex chars of SHA-256) over value (rounded
to 12 significant decimals), canonical unit, provenance fingerprint and label. A `COMPUTED` value
records the ids of its inputs in `provenance.input_ids`, which makes the derivation graph
reconstructible from the values alone.

`MeasurementSeries` is the raw-observation counterpart (x/y arrays with units and shared
provenance, id prefix `s_`). It is the typical input to a driver's analysis.

## 7.2 `Provenance` and its kinds

`hos/core/provenance.py`.

| kind | meaning | constructor-enforced requirement |
|---|---|---|
| `MEASURED` | an instrument/assay observation | names the instrument/assay (`source_name`) or the actor |
| `LITERATURE` | retrieved from a curated database or paper | a `Citation` (auto-created from the source name and URL if not given) and retrieval timestamp |
| `COMPUTED` | deterministic output of a cited equation | a `Method` (which itself must carry ≥ 1 citation) |
| `PREDICTED` | output of a named, versioned model | a `Method` **and** an `ApplicabilityCheck`; out-of-domain adds the flag `out_of_applicability_domain` |
| `GUIDELINE` | fixed by a regulatory guideline or reference table | a `Citation` |
| `USER_SUPPLIED` | entered by a named human | the actor |
| `SIMULATED` | generated by a declared model for verification/demonstration | a `Method` and the generator parameters (and seed) in `notes`; **never admissible as evidence** |
| `UNAVAILABLE` | could not be obtained | a reason |

There is deliberately no `DEFAULT`, `ASSUMED` or `ESTIMATED` kind.

`ProvenanceKind.admissible_as_evidence` is false for `SIMULATED` and `UNAVAILABLE`. Everything
downstream that produces a regulatory artefact checks it (the kernel's approval gate and the IND
assembler, see `docs/10`).

Other fields: `source_url`, `source_record_id`, `retrieved_at`, `actor`, `input_ids`, `software`
(library → version, e.g. `{"rdkit": "2026.09.1"}`), `parameter_set_version` (reference-parameter
registry version used), `applicability`, `reason`, `notes`, `recorded_at` (UTC).
`fingerprint()` hashes the provenance-defining fields (excluding the timestamp) so identical
derivations produce identical ids.

## 7.3 Citations and methods

- `hos/core/citations.py` — `CITATIONS: dict[str, Citation]`, 42 entries. Each has a stable key,
  full reference text, and DOI or URL. Journal entries were checked against Crossref by DOI and
  ICH entries against the official PDFs (`docs/09` §9.4).
- `hos/core/methods.py` — `METHODS: dict[str, Method]`, 27 entries. A `Method` has an id, semantic
  version, name, ≥ 1 citation, and explicit `assumptions` and `limits` that travel with every value
  it produces. `Method` construction fails without a citation.

Method families: `descr.*` (RDKit descriptors), `rule.*` (Lipinski, Veber), `adme.*` (depletion
fit, CLint, fu,mic, scaling, well-stirred CLh, extraction ratio, fu,blood), `pharm.hill_4pl`,
`safety.herg_margin`, `dose.hed_bsa`, `dose.mrsd`, `sim.*` (simulation generators).

## 7.4 Reference-parameter registry

`hos/core/reference_params/__init__.py`. Physiological and scaling constants are data, not
literals: each `ReferenceParameter` has `id` (e.g. `qh.human`), value, unit, description,
`citation_key`, species, `requires_verification`, note. `as_quantity()` returns a `GUIDELINE`
quantity stamped with the registry version (`REGISTRY_VERSION`). A parameter flagged
`requires_verification` adds the QC flag `reference_value_requires_verification` to every value
computed from it, so an unverified constant is visible in the final result.

Changing any value requires bumping `REGISTRY_VERSION`; results record the version they used and
are never silently recomputed. The verification status of each value is in `docs/09` §9.4.

**Separately versioned tables.** `ReferenceTable` holds a cited table that has its own version,
for constants unrelated to the physiological registry. Bumping `REGISTRY_VERSION` would change
the provenance, and so the analysis hash, of results already signed.

The first such table is `RESIDUE_MASS_TABLE` (`expasy-findmod.2026-10-11`), which holds the
ExPASy average residue masses and water. Its values were transcribed by script from the page,
whose hash is in `docs/research/sequence_entities.md`.

## 7.5 QC verdicts

`hos/core/qc.py`. `QCFinding(code, status ∈ {PASS, WARN, FAIL}, message, observed, threshold)` and
`QCVerdict` (worst status wins). A `FAIL` from an analysis step makes the dependent quantities
`UNAVAILABLE` with the failure message as the reason (e.g. no depletion ⇒ no rate constant ⇒ no
CLint ⇒ no CLh). `WARN` codes are attached to values as `qc_flags`.

## 7.6 The provenance ledger

`hos/kernel/ledger.py`. Append-only, hash-chained. Each `LedgerEntry` has:

`seq`, `recorded_at` (server UTC), `actor_id`, `actor_kind` (human/agent/system), `action`,
`subject_type`, `subject_id`, `payload` (JSON), `payload_sha256`, `prev_hash`, `entry_hash`,
`reason`.

`entry_hash = SHA-256(canonical_json(body))` where the body includes `prev_hash` and
`payload_sha256`; the first entry chains from 64 zeros. `Ledger.verify()` walks the chain and
raises `LedgerIntegrityError` on a sequence gap, a broken link, an altered payload, or an entry
whose hash does not match its contents. Backends: `MemoryLedgerBackend` (tests) and
`SqlLedgerBackend` (`hos/db/store.py`, table `ledger`).

**Hashing schemes.** Scheme 1, used for entries written before docs/15 P0.3, hashes the whole
body. Scheme 2, used for every new entry, hashes the previous hash together with a digest of the
rest of the body:

`entry_hash = SHA-256({"scheme": 2, "prev_hash", "content_digest"})`

So an entry can be shown to a third party as (`prev_hash`, `content_digest`, `entry_hash`)
without its content, and the chain still recomputes. A Module 4 bundle shows other programmes'
scheme-2 entries only in that redacted form. Scheme-1 entries are shown in full, since redacting
them would break the chain. The verifier recomputes both schemes and refuses a redacted line
that carries anything more.

**Reconciled and anchored** (docs/15 P0.2, `hos/kernel/integrity.py`).
- *Reconcile.* `Kernel.integrity()` checks every stored record against the ledger events that
  created or last changed it:
  - principals against their registration;
  - programme study sets (and so contexts) against their last programme event's hash;
  - guests against a replay of their membership events;
  - compounds against their registration (structure, or sequence fingerprint);
  - a study's state against its last state event;
  - protocol, data, analysis and report against the hashes their events recorded, recomputed
    from the stored content. The rendered report text is covered by `report_record_hash`, or
    by the report artefact for older events;
  - signatures and determinations against their own events;
  - artefacts against their stored hashes.

  This catches rows edited straight in the database, which the chain alone cannot see.
- *Anchor.* After every unit of work, the head (sequence, hash, time) is appended to a log outside
  the database. By default it sits beside the file store; for production, point `HOS_ANCHOR_DIR`
  at write-once storage. With `HOS_ANCHOR_KEY` set, every checkpoint carries an HMAC.
  - A truncated chain no longer reaches a checkpoint.
  - A chain rewritten and re-hashed no longer passes through the anchored heads.
- `/api/ledger/verify` reports all three. Its findings go to administrators only, because they
  name subjects across programmes; everyone else gets a count.

**Atomic with the state it records** (docs/15 P0.1). Every kernel operation that writes is an
`@atomic` unit of work (`hos/kernel/uow.py`, `Database.transaction`). Its state changes,
artefacts and ledger entry share one database transaction, so either all commit or none does.
- Nested operations join the outer unit; only the outermost commits.
- Writers are serialised within the process. Across processes, the primary key on `seq` refuses
  a second entry with the same number, which rolls that writer's whole change back. SQLite
  connections wait up to five seconds for the write lock.
- A refusal that must stay on the record while the call fails, such as a failed login, a rejected
  upload or a refused approval, raises `CommitThenRaise`.
- Tests make the ledger write fail before every step of a full lifecycle and check that no table
  changes. A static test checks that every writing kernel method is `@atomic`.

## 7.7 Principals and signatures

`hos/kernel/attestation.py`. `Principal(id, name, kind ∈ {HUMAN, AGENT, SYSTEM}, roles)`. Roles
include the four legal attestors (`STUDY_DIRECTOR`, `QUALITY_ASSURANCE`,
`ATTENDING_VETERINARIAN`, `QUALIFIED_PERSON`) and working roles. `sign()` refuses non-human
principals, roles the principal does not hold, and empty statements. A `Signature` binds signer
id and name, role, meaning (authorship / review / approval / responsibility / QA compliance),
subject id, **subject hash** (SHA-256 of the exact record signed), UTC time and statement.

**Access** (docs/15 P0.3).
- A programme belongs to its creator's organisation (`programs.organisation`; None is the default
  organisation). It is visible to that organisation and to guests added through
  `program_members`, such as a CRO. Adding or removing a guest needs a person of the owning
  organisation and a reason, and is ledgered.
- Every API route that names a programme, study, compound, file or ledger subject checks access
  before its handler runs, and answers 404 when the caller is out of scope. Files reach
  programmes through `file_links`, because identical bytes can belong to more than one
  programme. Lists are filtered the same way.
- An organisation's administrator lists and registers principals in that organisation only.
- A test walks every route with another organisation's ids.

**Identity** (21 CFR 11.300; docs/15 P1).
- *Sessions* (`sessions` table) store only the SHA-256 of the token. They have an absolute
  timeout (`HOS_SESSION_HOURS`, default 8) and an idle timeout (`HOS_SESSION_IDLE_MINUTES`,
  default 30), and can be revoked server-side, so they survive restarts and are shared between
  workers. Agents get revocable keys (`HOS_AGENT_KEY_DAYS`, default 90). Sign-in and sign-out
  are ledgered.
- *Lockout.* Consecutive failed attempts, at sign-in or at a signature's re-authentication,
  lock the account at `HOS_LOCKOUT_ATTEMPTS` (default 5) until an administrator unlocks it.
  Only someone who supplies the correct password is told the account is locked. Sign-in is
  also throttled per client address (`HOS_LOGIN_ATTEMPTS_PER_MINUTE`, default 10).
- *Lifecycle.* An administrator of the user's organisation can deactivate or reactivate a user,
  change roles, unlock, and reset a password. A reset forces a change at the next sign-in, and
  nothing else is allowed until then. Each action carries a reason and is ledgered, and
  reconciliation replays role changes and deactivations. A deactivated user can neither sign
  in nor sign; their earlier signatures keep verifying.

## 7.8 Persistence

`hos/db/models.py` (SQLAlchemy 2.x). Tables: `principals`, `programs`, `compounds`, `studies`,
`files`, `ledger`. A compound has a `kind`:
- `small_molecule` compounds are registered by SMILES, with an RDKit profile;
- `sequence` compounds are peptides or antibodies registered by one-letter chains or a HELM
  string (`hos/kernel/entities.py`, docs/14 P4). The entity stores the registered spec, a
  fingerprint and the facts derived from it. Drivers see no SMILES, and the average mass where
  one is defined.

SQLite by default (`~/.hakase_os/hos.sqlite3`); `HOS_DATABASE_URL` selects
PostgreSQL. Raw files go to `FileStore`, a content-addressed object directory keyed by SHA-256;
`get()` re-hashes on read and raises if the bytes changed.

Known gaps: schema is created with `create_all()`; Alembic migrations are **(planned)** before
any shared deployment. The kernel facade that writes these tables is built in build step 5
(`docs/11`).

## 7.9 Serialisation

Every object above has `to_dict()`. API payloads (build step 9) carry the full `Quantity.to_dict()`,
including provenance and citations, so the frontend can render the provenance badge and its
derivation without computing anything.
