# Domain Model Specification

# 1. Purpose

The Domain Model Specification defines the conceptual data model of the HakaseAI Peptide Discovery Platform.

It establishes the core scientific and computational entities that collectively describe the platform's operation, independent of any programming language, database technology, or software implementation.

The Domain Model provides a common vocabulary shared across all architectural layers, ensuring that Scientific Services, workflow orchestration, evidence generation, decision making, reporting, APIs, and storage systems all reference the same conceptual objects.

Rather than describing implementation details, this specification defines:

- the purpose of every domain object;

- the information represented by each object;

- relationships between objects;

- object ownership;

- lifecycle transitions;

- versioning strategy;

- serialization requirements;

- interaction rules.


This document serves as the conceptual foundation for future API specifications, database schemas, object models, and software implementation.

---

# 2. Scope

This specification defines the conceptual representation of the primary entities used throughout the HakaseAI platform.

The domain model includes:

- Peptide

- Target

- Scientific Service

- Evidence Object

- Platform Evidence

- Prediction

- Computational Model

- Dataset

- User

- Project

- Job

- Experiment

- Report


The specification intentionally excludes:

- database schemas;

- object-relational mapping;

- API contracts;

- storage implementation;

- software architecture;

- programming language constructs.


---

# 3. Domain Modeling Principles

The HakaseAI Domain Model is governed by the following principles.

## 3.1 Scientific First

Scientific entities represent biological or computational concepts rather than software components.

Objects describe scientific meaning independently of implementation.

---

## 3.2 Single Source of Truth

Every concept within the platform is represented by exactly one canonical object.

For example:

- a peptide is represented only by the **Peptide** object;

- computational evidence is represented only by the **Evidence Object**;

- workflow execution is represented only by the **Job** object.


Duplicate conceptual representations are prohibited.

---

## 3.3 Separation of Concerns

Scientific objects remain independent from infrastructure objects.

Examples:

Scientific Objects

- Peptide

- Target

- Prediction

- Evidence


Infrastructure Objects

- Job

- User

- Project


Decision Objects

- Platform Evidence

- Report


This separation minimizes coupling across the platform.

---

## 3.4 Immutable Scientific Evidence

Evidence generated by Scientific Services is immutable.

Scientific findings are never modified after publication.

Corrections generate new versions linked through provenance.

---

## 3.5 Explicit Relationships

All relationships between objects must be explicitly defined.

Relationships shall never rely upon hidden references or implicit assumptions.

---

## 3.6 Traceability

Every object must remain traceable throughout its complete lifecycle.

Relationships between objects must enable reconstruction of:

- workflow execution;

- scientific provenance;

- computational dependencies;

- generated reports.


---

## 3.7 Versioned Objects

Objects evolve through explicit versioning rather than in-place modification.

Version history preserves scientific reproducibility.

---

## 3.8 Technology Independence

The Domain Model defines concepts rather than software implementations.

Individual software components may evolve without changing the conceptual model.

---

# 5. Core Domain Objects

---

# 5.1 Peptide

## Purpose

The Peptide object represents the canonical molecular entity analyzed by the HakaseAI platform.

Every computational workflow centers around exactly one Peptide object.

The Peptide object provides a standardized representation of the molecular sequence together with its chemical modifications and metadata.

It serves as the primary scientific subject consumed by every Scientific Service.

---

## Attributes

Every Peptide object contains at minimum:

|Attribute|Description|
|---|---|
|peptide_id|Globally unique identifier|
|sequence|Canonical amino acid sequence|
|sequence_length|Number of residues|
|modifications|Chemical modifications|
|molecular_formula|Molecular composition|
|molecular_weight|Optional reference value|
|peptide_type|Linear, cyclic, stapled, modified, etc.|
|organism|Source organism (optional)|
|metadata|User-defined metadata|
|creation_timestamp|Creation time|
|schema_version|Domain schema version|

---

## Relationships

The Peptide object:

Produces:

- Physicochemical Evidence


Consumes:

- none


Referenced by:

- Target

- Scientific Services

- Jobs

- Experiments

- Reports


Used to generate:

- all Evidence Objects


---

## Lifecycle

```text
Create
   │
   ▼
Validate
   │
   ▼
Canonicalize
   │
   ▼
Scientific Analysis
   │
   ▼
Archive
```

Once canonicalized, the biological identity of a peptide never changes.

Sequence modifications generate a new Peptide object rather than modifying an existing one.

---

## Ownership

Primary owner:

Project

Referenced by:

- Experiments

- Jobs

- Evidence Objects

- Reports


The Peptide object remains independent of any individual workflow execution.

---

## Constraints

Every Peptide object SHALL satisfy:

- valid amino acid representation;

- canonical sequence notation;

- globally unique identifier;

- immutable sequence after validation;

- explicit modification annotations.


---

## Versioning

Peptide objects follow semantic versioning.

Minor metadata updates increment the minor version.

Any modification to the biological sequence generates a completely new Peptide object with independent provenance.

---

## Serialization

Canonical serialization:

- JSON


Character encoding:

- UTF-8


Identifiers:

- UUID


Time representation:

- ISO-8601


---

## Interaction with Other Objects

The Peptide object interacts directly with:

- Scientific Services

- Target

- Job

- Experiment

- Evidence Objects

- Report


The Peptide object is the root scientific entity from which all computational evidence originates.

---

# 5.2 Target

## Purpose

The Target object represents the intended biological molecule, molecular complex, or biological system against which a peptide is evaluated.

Targets provide biological context for structural prediction, functional analysis, and downstream interpretation.

Not every workflow requires a Target object. Target-independent analyses remain valid.

---

## Attributes

|Attribute|Description|
|---|---|
|target_id|Unique identifier|
|name|Canonical target name|
|aliases|Alternative identifiers|
|organism|Source organism|
|target_type|Protein, receptor, enzyme, membrane, etc.|
|sequence|Optional amino acid sequence|
|structure_reference|Structural database reference|
|external_identifiers|UniProt, PDB, etc.|
|metadata|Additional annotations|
|schema_version|Domain schema version|

---

## Relationships

Referenced by:

- Structural Biology Service

- Functional Analysis Service


Associated with:

- Peptide

- Prediction

- Report


May reference:

- External databases


---

## Lifecycle

```text
Register
   │
   ▼
Validate
   │
   ▼
Reference
   │
   ▼
Archive
```

Targets are reference entities and are rarely modified after validation.

---

## Ownership

Targets are owned by reference datasets rather than individual users.

Projects may reference targets but do not own them.

---

## Constraints

Target objects SHALL include:

- unique identifier;

- biological classification;

- organism information;

- stable external references where available.


---

## Versioning

Target definitions are versioned independently from projects.

Updates to external annotations generate new target versions while preserving historical references.

---

## Serialization

Canonical JSON serialization.

References to external databases remain stable through persistent identifiers.

---

## Interaction with Other Objects

The Target object interacts with:

- Peptide

- Structural Biology Service

- Functional Analysis Service

- Computational Models

- Reports


The Target object provides biological context but does not generate scientific evidence.

---

# 5.3 Scientific Service

## Purpose

A Scientific Service represents an independent computational capability responsible for generating one category of scientific evidence.

Scientific Services constitute the computational core of the HakaseAI platform.

Each service performs one scientific responsibility only.

Examples include:

- Physicochemical Service

- Structural Biology Service

- Functional Analysis Service

- Developability Service

- Safety Service


Scientific Services never perform workflow orchestration or scientific decision making.

---

## Attributes

|Attribute|Description|
|---|---|
|service_id|Unique identifier|
|service_name|Canonical service name|
|service_version|Version identifier|
|scientific_domain|Supported scientific discipline|
|status|Active, Deprecated, Experimental|
|supported_modalities|Applicable peptide classes|
|supported_models|Registered computational models|
|evidence_type|Published Evidence Object type|
|metadata|Service metadata|

---

## Relationships

Consumes:

- Peptide

- Evidence Objects

- Datasets

- Computational Models


Produces:

- Evidence Object


Referenced by:

- Workflow

- Job

- Audit Records


---

## Lifecycle

```text
Register
   │
   ▼
Deploy
   │
   ▼
Execute
   │
   ▼
Publish Evidence
   │
   ▼
Version
   │
   ▼
Retire
```

Each execution is independent and stateless.

---

## Ownership

Scientific Services are owned by the HakaseAI platform.

Individual users cannot modify service definitions.

---

## Constraints

Each Scientific Service SHALL:

- perform exactly one scientific responsibility;

- publish exactly one Evidence Object per execution;

- preserve computational provenance;

- remain independent of downstream decision logic;

- avoid modifying upstream Evidence Objects.


---

## Versioning

Scientific Services use semantic versioning.

Major versions indicate scientific or architectural changes.

Minor versions introduce backward-compatible capabilities.

Patch versions correct implementation defects without altering scientific behavior.

---

## Serialization

Scientific Service definitions may be serialized as JSON or YAML configuration objects.

Execution metadata is recorded separately within audit logs.

---

## Interaction with Other Objects

Scientific Services interact directly with:

- Peptide

- Target

- Computational Models

- Datasets

- Evidence Objects

- Jobs

- Workflow Orchestrator


Scientific Services are the exclusive producers of computational evidence within the HakaseAI platform.

---

# 6. Summary

Part 1 of the Domain Model establishes the foundational scientific entities of the HakaseAI platform.

The **Peptide** object represents the central molecular entity, the **Target** object provides biological context, and **Scientific Services** perform independent computational analyses that generate standardized evidence.

Subsequent sections of this specification define the evidence model, computational prediction objects, infrastructure entities, and reporting artifacts that complete the conceptual domain model.
